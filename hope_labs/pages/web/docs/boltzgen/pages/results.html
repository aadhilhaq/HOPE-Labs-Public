What a run leaves

One folder per run, holding the structure that went in, the specification that was written from it, the job that was sent, BoltzGen's own output, and one small file that the rest of the lab's tools read.

The run folder

pdl1_20261003-1204/              the run, as the Runs screen lists it
  flow.json                      what was asked for, as a flow of two cards
  submission.json                who submitted it, when, the job id, the plan
  inputs/target.pdb              the structure, fetched or copied once
  state/boltzgen.json            what became of the card
  pdl1_boltzgen/                 the job's own folder
    plan.json                    what the job was told
    job.sbatch                   the script that was queued
    slurm_<jobid>.out            the log
    target.yaml                  the specification, hotspots converted
    checked/                     the specification written out and read back
    final_ranked_designs/        BoltzGen's own output, with its metrics tables
    designs.json                 the designs, best first
    cache/                       what the job wrote for itself

The two levels are not an accident. The outer folder is a flow of two cards, a target and the tool on it, which is exactly what the page submits and exactly what the canvas would have drawn; the inner one is the job's own. That is why a run queued from the canvas and a run queued here look the same on disk and can both be read here.

The specification, and the file that proves it

target.yaml is what BoltzGen was actually given: the chains kept, the binding residues as positions in the chain, and the binder asked for as a length range. It is short enough to read, and it is the file to look at if a run designed against the wrong patch.

checked/ holds the specification written back out as a structure, with a raised B-factor on every binding residue. That is how the conversion is proved without a GPU: the job reads those marks back and refuses to go on if they are not the positions it asked for. If the run got past that point, the hotspots were right.

designs.json

The one file anything else reads. It holds the designs best first:

{"tool": "boltzgen",
 "designs": [{"name": "pdl1_design_7",
              "path": ".../final_ranked_designs/final_30_designs/rank1_pdl1_design_7.cif",
              "binder_chains": ["B"],
              "target_chains": ["A"],
              "sequence": "GSHMKELAEQ...",
              "score": 1}]}

The score is BoltzGen's own final rank, so 1 is the best. Which chain is the binder is read out of each structure rather than assumed: BoltzGen renames the chains of what it writes, so the letter asked for in the specification is not the letter that comes out, and a binder can be the same length as a small target. The chains are matched on sequence instead, the designed sequence against the metrics table and the target's against the file that went in. A design where that cannot be settled is dropped and named in the log.

BoltzGen's own output

final_ranked_designs/ is BoltzGen's, not the page's, and is worth opening when a run has finished:

WhatWhat it holds
final_30_designs/The re-folded structures of the designs the tool recommends, named with their rank. These are the structures designs.json points at.
intermediate_ranked_10_designs/The earlier ranked set, which is what exists in the middle of a run.
the metrics tablesThe scores behind the ranking, one row per design and about thirty columns. designs.json keeps the rank; these keep everything the rank was made from, and they are what to read if you want to filter differently.

What the score is, and is not

The rank comes from BoltzGen's own re-folding. It generated the design, then predicted the complex again and scored what it predicted. That is a genuine filter and it is why the designs come out in an order worth trusting more than their generation order. It is still a model scoring a model's work, and it is not an affinity.

If the run was submitted with folding turned off, there is no ranking at all and designs.json is in no meaningful order.

Taking a design further

From the launcher's canvas, the designed complexes output of this card goes straight into HOPE-MD, which will simulate the binder on the target and compute a binding energy for it. The design sequences output goes into the docking instead, for designs short enough for it to take, which is thirty residues or fewer.

By hand: each structure named in designs.json is a complete complex in mmCIF and can be opened or handed to anything that reads one.

The report

Report (PDF), on a run you have chosen, opens that run written up as a page of its own, in a new tab, ready to save as a PDF. It is the run as you would describe it to somebody else: the selected designs with the numbers BoltzGen ranked them on, what each filter cost, the selection set against the whole population it was chosen from, the sequences to order, and the top design on the target; then the methods with their references, and an appendix holding the settings as asked beside the settings as the tool ran them, where the target came from, the versions, the job and the files.

The bar along the top is the report's own. Tick the sections you want and set how many designs the tables show; zoom with the minus, the percentage and the plus, or fit the width. Copy the methods and references puts the methods on the clipboard. Save as PDF opens the browser's print window, where the printer to choose is "Save as PDF". The zoom is yours and is kept in this browser; it never reaches the PDF, which always prints at full size.

Every caption states the result from the run's own numbers and then only what is needed to read it, rather than naming the table. So a ranking reads "Of 10,000 designs, four passed every filter, and the narrowest single filter is the refolding RMSD, which 912 passed", rather than "the designs ranked by score". Where a run has nothing to say, the caption says what is missing and what would fill it: a run made before the design helper recorded its confidence figures is told so, in the report, rather than shown an empty column.

Two things the report will not do. It writes nothing into the run folder: it only reads. And it shows no number the run did not write, so it and the Runs screen cannot disagree. There is no Add to report yet: this page has no viewer that can write into a run, so the structure figure is drawn by the report itself from the run's own file.
