The Runs screen

Every run you can read, newest first, with its Slurm state, what it has written so far, the ranked designs once it has finished, and the log.

The list

Mine lists the runs you submitted or own; Everyone lists every run in the folders this page was started with, which on a shared install is how you find a colleague's run. The dot on the left is the Slurm state: amber queued, teal and blinking running, green finished, rust stopped, and hollow for a run with no job, which is what a dry run looks like.

The list reads the run folders and the queue again every twenty five seconds while the screen is open, and not at all while it is put away. The circular arrow at the top right reads them at once.

What the tiles say

TileWhat it counts
designsHow many designs are in designs.json. That file is written when the run finishes, so a run still going shows a dash here rather than a zero: none written yet and none found are different things.
designs (on disk)How many structures are in the final ranked folder. This fills only at the end, after the analysis step, because that is when BoltzGen writes it.
consideredHow many structures are in the intermediate ranked folder. This is the honest measure of progress during the middle of a run.
asked forWhat was asked for when the run was submitted, with the card and the walltime beside it.

A BoltzGen run is quiet for a long stretch and then produces everything at once, which is worth knowing before you conclude it has stalled. The log is the better guide while it is in the middle of generating.

What was asked for

Under the tiles is the target, the hotspots, the binder length, where the results are and who submitted it, read from submission.json in the run folder. The buttons beside it download the files worth having: designs.json, the plan the job was given, the job script itself and the full log.

Cancel and Queue again

While a job is queued or running, Cancel the job runs scancel on it. Slurm decides whether you may: it is your job or it is not. What is already on disk stays in the run folder.

Once a job is over, the button becomes Queue again, which sends the same job script back to Slurm. It starts from the beginning: there is no checkpoint, so queueing again after a timeout repeats the work rather than continuing it.

The log

The last couple of hundred lines of the job's Slurm output, newest at the bottom, read fresh each time the run is opened. Full log downloads the whole file.

The log is where the run says what it is doing: the hotspot conversion and the line confirming it survived into the specification, the BoltzGen command line it ran, then the pipeline's own progress through its steps, then how many rows it read out of the metrics table and which designs were dropped. What the messages mean covers the lines worth knowing.
