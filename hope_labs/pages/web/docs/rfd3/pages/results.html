What a run leaves

The structures, the record the next card reads, and which chain is actually the design.

The structures

One file per design, written as compressed CIF and unpacked beside itself. Each holds the binder and the target together: the design arrives already placed, so docking it again is a choice rather than a necessity.

Beside each structure the model writes its own JSON of what it did, including the contig it actually sampled and, where a motif was scaffolded, where each constrained atom ended up.

Which chain is the design

Chain A, numbered from 1. Not the chain you named on the form.

The model relabels everything it writes in contig order, and the contig puts the design first. So a target that went in as chain A comes back as chain B, renumbered from 1. On a run against MDM2 the output is chain A of 61 residues, which is the design, and chain B of 85, which is MDM2 going in as A25-109.

This is worth knowing before opening one in a viewer, and the run records it explicitly: designs.json names the binder's chains and the target's rather than leaving it to be worked out.

designs.json

The record every design tool here writes, and the only thing a following card reads. One entry per design, best first:

  • name and path, the design and where its structure is
  • binder_chains and target_chains, as the output labels them
  • sequence, ProteinMPNN's best for that backbone
  • rfd3_sequence, the model's own, kept for comparison
  • score, ProteinMPNN's score for the kept sequence, lowest first

Because the format is the one RFdiffusion and BoltzGen already write, the cards that follow needed no change to accept these designs: a complex can go to HOPE-MD.

Why there are two sequences

The model writes a sequence as it diffuses, and ProteinMPNN writes another for the same backbone. They differ substantially. Neither is obviously right, so both are kept and the ProteinMPNN one is what is handed on, because it is the one the authors' own pipeline orders from and it comes with a score to rank by.

The report

Report (PDF), on a run you have chosen, opens that run written up as a page of its own, in a new tab, ready to save as a PDF. It is the run as you would describe it to somebody else: the ranking, the model's whole geometry block with the scope of every column, ProteinMPNN's sequences beside the model's own, the best design on the target with its hotspots mapped through the run's own index map, and the specification as the model resolved it; then the methods with their references, and an appendix holding the settings as asked beside the settings as the tool ran them, where the target came from, the versions, the job and the files.

The bar along the top is the report's own. Tick the sections you want and set how many designs the tables show; zoom with the minus, the percentage and the plus, or fit the width. Copy the methods and references puts the methods on the clipboard. Save as PDF opens the browser's print window, where the printer to choose is "Save as PDF". The zoom is yours and is kept in this browser; it never reaches the PDF, which always prints at full size.

Every caption states the result from the run's own numbers and then only what is needed to read it, rather than naming the table. So a ranking reads "Both designs are helical bundles with no chain break and no clash: one is 90 per cent helix in 2 elements, the other 79 per cent in 4", rather than "the designs ranked by score". Where a run has nothing to say, the caption says what is missing and what would fill it: a run made before the design helper recorded its confidence figures is told so, in the report, rather than shown an empty column.

Two things the report will not do. It writes nothing into the run folder: it only reads. And it shows no number the run did not write, so it and the Runs screen cannot disagree. There is no Add to report yet: this page has no viewer that can write into a run, so the structure figure is drawn by the report itself from the run's own file.
