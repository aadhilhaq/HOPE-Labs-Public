The Runs screen

Your runs, what Slurm makes of them, and the two things you can do to a job that is already queued.

The list

Newest first, with a dot for the state: amber for queued, teal and blinking for running, green for finished, rust for stopped. Mine shows yours; Everyone shows every run in the folders this page was started with, which is how to see what a colleague's run did without asking them.

A folder is a run when it holds a submission.json, and the page writes that before it queues anything, so a run whose submission failed is still listed and can still be read.

What the tiles say

Samples is how many structures are on disk, counted by looking rather than by reading the log. Before the job has finished, that count comes from the batches written so far, which is how you can watch a long run arrive. Shapes is how many distinct ones reading them found, and it appears only once the run has been read.

The sentence at the top of a finished run

One shape, or several with the share of the samples each holds, and how far the samples lie from the mean shape. It is the same sentence in the report and in a flow's record, written once so that all three say the same thing. The shapes, and what they are not explains what is behind it.

Cancel, and Queue again

Cancel runs scancel on the job. Slurm decides whether you may, which is to say it is your job or it is not. What is already on disk stays in the run folder.

Queue again submits the same job script a second time. It is phase two only, so it needs no network: the alignment is already in the folder. Use it for a run that ran out of walltime or died on a bad node. The sampling starts again from the beginning either way.

The log

The last couple of hundred lines of the Slurm log, under The log at the bottom of the run (open already when the run stopped early), with the whole file a download away. The job prints the node, the card and the driver before it samples anything, because when sampling fails on a new node it is almost always the card or the driver rather than the tool. If the node turns out to have no usable card at all, the job stops there rather than spending the booking on the processor.

What was sampled

Under The job it was given: the sequence as it was sampled and the job script exactly as it was queued, so an argument about what a finished run sampled can be settled from the run folder rather than from memory.

Tidying when it finishes

A run that finishes and has written its samples packs what its results no longer read into one archive in its own archive folder: the per batch arrays the samples were written from, which are the same numbers as the trajectory file, the embeddings made from the alignment, and the matplotlib and CUDA caches. The samples, the topology, everything under analysis, the alignment, the sequence and the log stay, and so does the home folder the image was given. A run that wrote nothing is left whole. Keep every file, under After the run on the form, leaves the run alone, and

python -m hope_labs.ensemble.tidy RUN --undo

run from the HOPE Labs folder puts every file back.
