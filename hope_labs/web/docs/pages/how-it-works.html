How it works

One SSH connection, held by the program on your computer, and every tool reached through it: started on the login node, found by the line it prints, and forwarded to a port on your own computer.

One connection

Signing in opens one SSH connection to a login node of the cluster: on Grace, with your password and one Duo approval. Everything after that goes through it. Each tool is started as a process on that connection, and each tool's page reaches your browser through a port forwarded over it. That is why Duo is asked once however many tools you open, and why signing out, or the connection dropping, stops every tool's page together.

Your password goes to the connection and nowhere else. It is not written down, logged, or offered back the next time.

Starting a tool

Each tool is started by one line of shell, kept with everything else HOPE Labs knows about the tools in hope_labs/tools.py. For the tools that serve their own page the line goes into the tool's install, enters its environment through the install's own activate.sh, or through the command its installer wrote, and starts the page server there. For the ones whose page is part of HOPE Labs it runs from the HOPE Labs checkout instead, looks for a Python of 3.8 or newer, and is handed the tool's install as a setting, which is how a copy of the tool in somebody's own scratch is still driven by the lab's page. Either way the server listens on the login node alone.

The tool then says it is ready by printing its port and a token, and HOPE Labs reads that off the connection it already holds. Every tool says so in the same way.

ToolWhat it prints when it is ready
Every tool One line with its own address, http://127.0.0.1: then its port and /?t= then its token. Each picks a free port itself.

HOPE Labs then forwards a free port on your computer to that port on the login node, and the tool's tab shows the page through it. A tool that prints nothing of the kind within two minutes, or stops first, is reported with the reason: see When something goes wrong.

Tokens

None of the tools takes its token on the command line, and that is deliberate: a login node is shared, and ps shows every process's arguments to everybody on it. Each tool makes its own token and prints it, and HOPE Labs reads it off the connection, where nobody else can see it. Every request to a tool's page has to carry it.

HOPE Labs' own page works the same way. It listens on your computer alone, and while the page itself loads without its token, every request for the session's state and every start or stop needs it. These docs are the one part that needs no token: they are the same for everyone.

The same port every time

The page is served on the same port of your computer every time you sign in, worked out from your account name. Chrome remembers what you allowed (the tabs reaching this computer, and pop-ups) per address, and the address includes the port, so a page that moved port every session would be asked again every session. If that port is busy, the next few above it are tried, then any free one, and the log says so.

What runs where

WhereWhat
Your computerHOPE Labs itself: the sign in window, the one SSH connection, the page in your browser, and the ports forwarded to each tool.
The login nodeEach tool's page server, started when you pick the tool and stopped when you stop it or sign out. It submits the work rather than doing it. The surfaces the viewer under Results draws are computed here too, by MSMS from the HOPE Labs checkout, in a few seconds each.
The compute nodesThe work: every job a tool submits, through Slurm, under your account.

The tools are not changed by HOPE Labs, and each tab shows the tool's own page as it would be without it. The one thing of HOPE Labs on the cluster is its folder: the checkout the pages of ours are served from, and the tools beside it. The checkout submits nothing and holds no state of its own.

The folding tools need the login node for more than the page. Fetching an alignment is the one part of a folding run that wants the network, and a compute node on this cluster has none. So Boltz-2 and ColabFold fetch the alignments on the login node, before anything is queued, and the prediction runs in a GPU job with no network at all. Each page's own docs explain the two phases.

Adding a tool

Everything that differs between the tools is in hope_labs/tools.py: one entry per tool, giving where it is installed, the line that starts it, how it says it is ready, and where its runs are. A new tool either prints the ready line above or brings a reader of its own. Nothing else in HOPE Labs knows one tool from another.

An entry alone is half a tool, though, so a tool goes everywhere it can go before it is considered added. Six places:

WhereWhat it is
A tileIts entry in hope_labs/tools.py, with a category and the line that starts it.
A pageIts own, inside the install, or one of ours when the project ships none.
Its documentationServed at that page's /docs/, and auditing clean: every page in the sidebar present, every link and picture resolving.
A flow cardIts card in hope_flow/cards.py, with sockets saying what it needs and what it leaves.
These pagesAt the least a row in the tool table on the Overview.
A markA glyph of its own, which no other tool uses and which is not another tool's borrowed.
