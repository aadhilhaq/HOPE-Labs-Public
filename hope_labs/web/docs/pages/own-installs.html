Installing by hand

Set up installs some of the tools for you. The others are installed by hand, once, in the HOPE Labs folder, where HOPE Labs finds them without being told.

Start with Set up. Setting up on a cluster sets HOPE Labs up in a folder you choose and installs the tools it has a recipe for. This page is for the others, and for a tool you would rather install yourself.

The HOPE Labs folder is the one you set HOPE Labs up in, with its checkout at <folder>/HOPE-labs; replace <folder> with it everywhere below. Some of the tools are opened by a page that is part of HOPE Labs rather than of the tool, and that page is served from the checkout.

The tools with an installer of their own are the sections below. The others are the tools whose page is ours, where what there is to say is where each one lives and what it must not be made to share.

Before you start

Every tool below is a public project, installed from its own address. HOPE-MD is the HOPE Lab's, free for academic research and teaching under its own license.

The clone lines below are each repository's own address, in the form its own documentation gives it. For a private repository either form wants your own GitHub access: an SSH key on the login node, or a token for the HTTPS lines.

Check your file count, not your disk space. Grace caps the number of files as well as the bytes.

showquota

Read the File Usage column. An environment with AmberTools in it is about 60,000 files by itself, and personal scratch on Grace allows 250,000, so a few tools fill it. Clear space with conda clean -a -y, take the smaller environment where a tool offers one, or set HOPE Labs up in a group folder with more room.

Tools that come as one file

Some tools are installed as a container image instead of an environment: one file, however much is inside it, against the tens of thousands of files a Python environment costs. HOPE Labs builds these from its public repository and publishes them, so pulling one needs no account and no token:

cd <your HOPE Labs folder>
export SINGULARITY_CACHEDIR=$PWD/setup/cache/singularity
singularity pull images/bioemu_1.4.1.sif docker://ghcr.io/aadhilhaq/hope-labs-bioemu:1.4.1

The Set up page does this for you, and removes the image again when you take the tool off. An image carries no model weights: those are fetched separately, on a login node, into weights/<tool>/ beside it, because a compute node here has no network. A job then runs the tool inside the image with that folder bound in, and with the network shut, so a weight that was never fetched fails plainly instead of hanging.

A cluster cannot build these images, only pull them: building needs a privilege Grace does not give. They are built on GitHub's machines from the recipes in images/, and each image records the commit it was built from.

Nothing in your home directory. Home on Grace is 10 GB and 10,000 files. HOPE-MD's installer refuses a prefix under $HOME, and the pages of ours refuse to put a run folder in your home directory for the same reason. Always give a prefix.

Install from a login node. Each installer downloads something, and Grace's compute nodes have no outbound network.

Use the HOPE Labs folder for all of them. HOPE Labs looks for every tool under the folder it was set up in, in the layout below. Give <folder> to each installer as its prefix and you get exactly that layout.

HOPE-MD

P=<folder>
git clone https://github.com/aadhilhaq/HOPE-MD.git $P/HOPE-MD/MD && bash $P/HOPE-MD/MD/install.sh $P

That gives <prefix>/HOPE-MD/MD for the checkout and <prefix>/HOPE-MD/env for its environment, with caches in <prefix>/HOPE-MD/.cache. The environment is a venv on a base Python that already has OpenMM, PDBFixer, pdb2pqr and AmberTools. The script looks in HOPEMD_BASE_PYTHON first, and failing that builds a conda environment in <prefix>/HOPE-MD/conda, which its README calls tens of thousands of files. A Python of your own that already has those four is named with HOPEMD_BASE_PYTHON, and that build is skipped.

The script then checks that HOPE-MD imports and audits which of its module load lines work here, which takes a minute or two. The engines are never installed: they are Grace's own modules. Its README's Requirements table is plain about what that needs, and none of it is yours to grant: the amber group for every run, the desmond group for Desmond runs, and HPRC's Schrödinger users list for Prime MM-GBSA. Each is a mail to help@hprc.tamu.edu after registering with the authors.

The tools whose page is ours

RFdiffusion, RFdiffusion3, RFD4-Proteina, BoltzGen, Boltz-2, ColabFold and BioEmu are the tools whose page is not inside the install. None of those projects ships one, so the lab wrote them: the design pages are under hope_labs/pages, the folding pages under hope_labs/folding and the ensemble page under hope_labs/ensemble, and the Tools screen starts each from the HOPE Labs checkout rather than from the tool.

Because the page belongs to HOPE Labs, a copy of any of them elsewhere is still driven by the lab's page, which is handed the install path. A HOPE Labs checkout is named with HOPELABS_INSTALL, and the Python that runs the page with HOPELABS_PYTHON: the page needs Python 3.8 or newer, and a login node's own python3 may be older.

Two of them are installed as a single container image rather than as an environment: RFD4-Proteina and BioEmu. The install their page is handed is that image file, and the folder holding it is where their weights are read from, so a copy of the image in your own scratch brings its own weights with it. Tools that come as one file says how Set up installs them.

Each page serves its own documentation at its Docs button, written for the tool it fronts rather than for the launcher, and that is where the settings, the messages and the run folder are described.

RFdiffusion with ProteinMPNN

A card on the canvas as well, and a page and a card queue the same run through the same code.

ML_programs/RFdiffusion holds the code and its nine checkpoints, and envs/SE3nv is its environment, a Python 3.9 with torch. ML_programs/dl_binder_design is the ProteinMPNN half, with its own weights under mpnn_fr/ProteinMPNN. Both halves run in SE3nv: ProteinMPNN needs only torch and numpy, and that environment has them.

envs/proteinmpnn_binder_design is not used, and does not work. It has no Python standard library at all: 78 conda packages and no lib/python3.11, so its interpreter cannot start whatever its permissions say. Rebuild it only if something outside HOPE Labs wants it; the card does not.

RFdiffusion3

A card on the canvas as well, and a page and a card queue the same run through the same code.

envs/rfd3 is the environment, a Python 3.12 with rc-foundry and torch; ML_programs/foundry is the source it is installed from, kept because the model is driven through that checkout's own configuration; and ML_programs/foundry_checkpoints holds the 2.5 GB checkpoint, fetched on a login node because a compute node has no outbound network.

It cannot share anything with RFdiffusion above it. That one is Python 3.9 in SE3nv and this needs 3.12, so they are two installs and two cards, and nothing has been retired. The sequences, though, come from the same dl_binder_design ProteinMPNN the older tool uses.

Installing it needs one pin that pip will not work out. pip install ".[rfd3]" on its own resolves atomworks to a version whose configuration has drifted from the model's, and the first run dies on a renamed argument. The package names atomworks==3.0.1 in its own ci-constraints.txt and that is the version to install. The MPNN that ships in the same package is deliberately not used: its documentation asks that the original be used for anything being compared until the re-implementation has been validated, and it wants weights this install has not got.

BoltzGen

A card on the canvas as well, queueing the same run as the page.

envs/boltzgen is BoltzGen 0.3.2 on Python 3.12, and envs/boltzgen_cache holds its weights: five checkpoints and mols.zip, about 8 GB. It cannot share the Boltz-2 environment beside it, because boltz pins numpy below 2 and boltzgen pins 2.0.2: pip installs the second over the first without saying so, and leaves Boltz-2 broken. To install it again, elsewhere:

conda create -p <prefix>/envs/boltzgen python=3.12 && <prefix>/envs/boltzgen/bin/pip install boltzgen
HF_HOME=<prefix>/envs/boltzgen_cache <prefix>/envs/boltzgen/bin/boltzgen download all \
    --cache <prefix>/envs/boltzgen_cache

Fetch the weights on a login node: a compute node has no internet, and a cache missing one checkpoint fails when the model loads rather than when the job is submitted.

One thing to know before reading a BoltzGen spec by hand: it numbers the residues a binder should touch by their position in the chain, not by the numbering the structure file carries. On the lab's own hPD-L1, whose file begins at residue 18, residues 54 and 56 are positions 37 and 39. The card takes the file's numbering, as every other tool here does, and converts; it then runs boltzgen check and reads the marked residues back before queueing anything, because getting this wrong does not fail. It designs against a different patch of the surface and returns binders for the wrong site.

Boltz-2

envs/boltz is the environment, and envs/boltz/cache holds the weights, already fetched. The page always passes that cache to boltz, and that one argument matters more than it looks: left off, boltz falls back to ~/.boltz, finds nothing, and tries to download the whole 7.6 GB from a node with no route out, which is the single most likely way for a first run to fail. Keep the cache inside the environment's folder and a copy elsewhere needs no second setting.

conda create -p <prefix>/envs/boltz python=3.11 && <prefix>/envs/boltz/bin/pip install boltz
<prefix>/envs/boltz/bin/boltz predict --cache <prefix>/envs/boltz/cache <a tiny input>

There is no download subcommand: Boltz-2 fetches what it needs the first time it predicts, so run one small prediction on a login node to fill the cache before any job needs it. The whole cache is about 7.6 GB, most of it two checkpoints and a folder of 45,000 small molecule files.

This is the environment BoltzGen must not be installed into, for the numpy pins described there. The two are separate environments on purpose, even though BoltzGen re-folds its own designs with Boltz-2.

ColabFold

envs/colabfold is the environment, and the AlphaFold weights are in a params folder inside it.

Two things about it are worth knowing before anybody rebuilds it. The weights that are complete in this install are AlphaFold-Multimer's, so that is the model the page asks for, for one chain as well as for twelve; ColabFold's own auto would choose the single-chain model, of which this install has one parameter file of the five, and it would go to the internet to look before it looked at a single file. And relaxation is not offered at all, because OpenMM and PDBFixer are not in that environment, so a run that asked for it would fail at the very end with the folding already done.

Neither folding tool has an installer in this repository. Install either from its own project, github.com/jwohlwend/boltz and github.com/sokrypton/ColabFold, fetch the weights on a login node, and point HOPE Labs at the environment you built.

Pointing HOPE Labs at your copies

HOPE Labs reads a small settings file on your own computer, not on the cluster. On macOS and Linux it is ~/.hope_labs_public.json; on Windows it is %USERPROFILE%\.hope_labs_public.json.

Two keys matter. "root" is one folder holding every install, and each tool is looked for under it with the layout in the table above. "installs" names a tool on its own and wins over "root". Its keys are the tool keys: rfdiffusion, rfd3, rfd4, boltzgen, boltz2, colabfold, hopemd, bioemu.

{
  "root": "/scratch/user/jane.doe",
  "installs": {
    "hopemd": "/scratch/user/jane.doe/HOPE-MD/MD",
    "boltz2": "/scratch/user/jane.doe/envs/boltz"
  }
}

With neither key set, HOPE Labs finds every tool in the HOPE Labs folder of the cluster you sign in to. The file is read when you sign in, so sign out and in again after an edit. HOPE Labs keeps the sign in boxes in the same file and leaves what you wrote by hand alone. If the file named any installs, the log lists each tool key and its path just after you sign in, so you can see it was read.

To try a root without editing the file, set HOPE_LABS_ROOT in the environment HOPE Labs is started from. It wins over the file's "root".

Where runs go

Where a tool writes its runs is a separate question from where it is installed. What each repository documents:

ToolRuns folder, as its own documentation gives it
RFdiffusion$SCRATCH/rfdiffusion_runs
BoltzGen$SCRATCH/boltzgen_runs
Boltz-2$SCRATCH/boltz2_runs
ColabFold$SCRATCH/colabfold_runs
HOPE-MD/scratch/user/<NetID>/hopemd_runs

RFdiffusion's, RFdiffusion3's, BoltzGen's, Boltz-2's and ColabFold's are decided by HOPE Labs rather than by the tool, since the tool has no opinion about it: each is a command line that writes where it is told. They are in your own scratch because a folding run is gigabytes, and a path inside your home directory is refused outright with the reason.

Those are among the folders Results looks in, so runs from your own copies are listed there too.

If something goes wrong

When a tool will not start, its tab says why in one sentence, and the sentence names the folder it looked in. When something goes wrong lists every one, with what to do.
