Protocol and compute

How long, how many repeats, at what temperature and pressure; then where the jobs run, for how long, and what the run will cost before you submit it.

Presets

A preset fills the protocol with a known set of values, and every field stays editable. The page opens on Standard. Changing the length, the replicates, the time step or the save interval afterwards makes the protocol a custom one.

The seed

The seed decides where the build puts the ions and how each replicate starts: its velocities and its thermostat. -1 draws new ones every run. A number of your own, 0 to 2 000 000 000, builds the same system and starts every replicate the same way, each offset from it so the replicates still differ. Amber then repeats the run bit for bit on the same type of GPU; on the other engines a repeat starts the same but may drift apart, as their GPU arithmetic is not guaranteed to repeat in the last digits.

Heating and equilibration

Each replicate first runs the same ladder, as one GPU job, before its production:

  1. Minimize, 5 000 steps, with the solute's heavy atoms restrained.
  2. Heat from 0 K to the temperature over 200 ps at constant volume, the solute still held.
  3. Equilibrate for 1 ns at constant pressure, in four stages of 250 ps, the restraint on the solute's heavy atoms released from 5 to 1, 0.1 and then 0 kcal/mol/Å².

The ladder runs at 2 fs on every engine, whatever the production's step. Desmond replaces the minimization with 100 ps of Brownian dynamics at 10 K. A bilayer on Desmond relaxes with Schrödinger's own membrane protocol instead, about 0.5 ns; on the other four engines a bilayer's lipids are never restrained.

Production in segments, and resuming

A replicate's production is one job when it fits in the partition's time limit, and a chain of segments when it does not: each segment is a job of its own that starts where the one before ended. The number of segments is in the run plan, on the production line. A production job asks for one and a half times its estimated time with 30 minutes on top; when that passes the partition's limit, or the segment cap, the production is cut into segments short enough to fit, and each asks for the limit.

Each engine writes a restart point every few minutes of the run. A segment that is stopped, by its walltime or by a cancel, continues from its last restart point when it is submitted again with Start again on the Runs screen; the frames it wrote past that point are cut first, so none repeats in the trajectory. On Desmond the engine checkpoints itself 25 minutes before the walltime and the log says to resubmit, while a segment canceled before that runs again from its start. See Start again.

GPU auto

auto: fastest free now takes, at Submit, the fastest GPU type with a free card, and the partition that carries it: on Grace the A100, then the A40, the RTX and the T4; on ACES the H100, then the A30. On Grace A40 nodes can sit idle while A100 jobs wait, which is what auto is for. With nothing free, the run waits for the default type, or for the fastest type the partition you chose carries. The run plan says what auto would take now, from the free cards it counted, and the type it took is written into the run, so the run says what it ran on.

Walltime

The walltime field fills itself from the estimate as the settings above change. A walltime you type becomes each production job's limit: a longer one gives a slow node room, a shorter one cuts the run into more segments. Use the estimate, which appears under the box once you have typed in it, puts the estimate back, and so does emptying the field. Write it as HH:MM:SS or D-HH:MM:SS. It cannot pass the partition's limit: 96 hours on Grace's gpu and gpu-a40, 48 on ACES's gpu and 2 on its gpu_debug. A longer run is chained as segments instead.

The CPU check

For when the GPU queue is full and the question is only whether the pose holds for the first few nanoseconds. The CPU check preset runs on one whole CPU node (48 cores on Grace, on the medium partition), Amber or GROMACS only: OpenMM on a CPU is too slow to be worth a node, and the NAMD and Desmond builds here are for GPUs. It is at most 10 ns and 500 frames. It answers whether the pose holds at the start, not how it behaves.

The estimate

The Run plan, in the rail above Submit, is worked out from the settings as they stand. It appears once there is something to run, and it is the stages in order, numbered, each with where it happens and how long it should take: Prepare where one is needed, the build, the ladder, the production, the analysis, MM-GBSA and the tidy. The production line also carries the speed in ns/day and the segments the run is cut into. Under them: the atoms (marked est. until the structure's own count is known), the box, the whole run's time, the disk per replicate, the folder the results land in, and, on Grace, your quota when it is close to full: see The quota.

Show the job, under the plan, prints what the queue will actually be asked for: every job of the graph, what it waits for, and the #SBATCH lines of its script. It renders in memory and writes nothing.

The speed comes from finished runs on the same cluster, GPU type and engine, each scaled to this system's atoms and time step, taking the median. Until there are some, a seed table of published benchmarks stands in, and the plan's ? says which, for example from 3 finished amber runs on a100 (grace) or first run on a40 here: seed table, treat as a guess. The other stages come from finished jobs of the same kind in the same way. Every run adds its own rows when it ends, in the tables of its runs folder, and the maintainer merges the lab's rows into the tables every install reads, so the estimates improve with use.

How close it is

The atoms are measured from the structure as tleap's solvation will treat it: its principal axes, the box that holds it, and the waters that fill that box. Against the builds on Grace they come within 2 % once Prepare has run or when the files carry their hydrogens, and within 4 % from a file without them. Side-chain atoms a file lacks are rebuilt by the build, which can make the box larger than the estimate says. Desmond's box is estimated from its own rule. The run's own Jobs table, on the Runs screen, puts the measured times beside the estimate once the jobs have run.

The quota

Scratch on Grace counts files as well as bytes: 1 TB and 250 000 files. The Setup page reads your use with showquota and sets it beside what the run will write before its tidy job:

  • it says Quota: and the numbers when the run fits;
  • it warns in red, Close to the quota, when the run takes the files or the bytes past 90 % of the limit;
  • Submit refuses a run that cannot fit, beginning This run cannot fit in: tidy or delete finished runs, or open a runs folder in another space;
  • when the quota cannot be read, Submit goes ahead and says The quota was not checked.

This is why every run ends with tidy, which packs a finished run's small files into one archive; unticking pack small files when done skips it.
